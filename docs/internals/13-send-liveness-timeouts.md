### موثوقية الإرسال — مهلات الإقلاع والإيقاف (إصلاح 2026-07-30)

- **العلة المشخّصة**: عملية `codex app-server` حيّة غير مستجيبة كانت تعلّق الدور في
  «يستعد» بلا نهاية (`request()` وعد عارٍ بلا مهلة في تسلسل الإقلاع)، وتعليق
  `turn/interrupt` عند الإيقاف كان يعلّق `stopAll` فيحبس قفل `sendRequestBusy` في
  `main.js` إلى الأبد — كل رسالة لاحقة ترتد «انتظر اكتمال بدء الطلب السابق» حتى
  إعادة تشغيل التطبيق. نفس البنية في مسار SDK حين يعلق `agent.start` قبل الحسم.
- **الإصلاح**: `request(method, params, timeoutMs?)` في `codex.js` صار يقبل مهلة
  اختيارية (الطلبات بلا مهلة كما كانت)؛ طلبات الإقلاع الخمسة
  (initialize/thread-resume/thread-start/compact/turn-start) مقيدة بـ
  `BOOT_REQUEST_TIMEOUT_MS=60000` فتفشل صريحاً في مسار catch القائم
  (spawn_error + result خطأ + cleanup يقتل العملية)، و`turn/interrupt` في `stop()`
  مقيد بـ`INTERRUPT_TIMEOUT_MS=5000` ثم cleanup (نمط forceClose في SDK). وفي
  `main.js`: `stopAll(false)` داخل مسار الإرسال داخل `Promise.race` بسقف
  `STOP_ALL_SEND_TIMEOUT_MS=15000` (المقابض تُسحب مزامنةً وأحداث الدور القديم
  محجوبة بـ`runSeq`)، و`await agent.start` بسقف `SDK_START_TIMEOUT_MS=90000` —
  التجاوز يعيد رسالة عربية ويوقف التشغيل اليتيم عند حسمه المتأخر. تجاوز البيئة
  `SATR_CODEX_BOOT_TIMEOUT_MS`/`SATR_CODEX_INTERRUPT_TIMEOUT_MS` (‏100..600000)
  للاختبار القطعي حصراً.
- **التحقق**: `npm run test:send-liveness` (قطعي، بلا شبكة — fixtures بنمط
  `CODEX_BIN=node`): إقلاع صامت يفشل خلال المهلة بدل الصمت الأبدي، إيقاف على قناة
  ميتة يُحسم خلال المهلة، وحرس نصية على حصون main وحدود تجاوز البيئة؛ مسجل في
  `test:full`. عقود Codex الخمسة (contract/steer/compact/account/mcp-panel) أعيد
  تشغيلها خضراء بعد التعديل، و`eval:agent` ‏12/12.


### انقطاع الشبكة أثناء الدور — التصنيف والمراقب (2026-09-13)

- **العلة المقيسة**: سجل `WLAN-AutoConfig` أثبت سقوط الواي-فاي (نقطة اتصال هاتف عبر محوّل
  TP-Link USB — «disconnected by the driver») من 14:49 إلى 15:47؛ الدور بدأ 15:33 داخل
  الانقطاع، فأعاد Claude Code المحاولة ~3 دقائق **صامتاً** (رسائل `system/api_retry` كانت
  تُمرَّر خاماً وتتجاهلها الواجهة) ثم أخرج `API Error: Can't reach the API server … (ENOTFOUND)`
  وخرج برمز 1، فألصقت الواجهة صندوقاً ثانياً «فشل تشغيل أمر Claude Code — تأكد أنه مثبت
  ومسجّل دخوله». ثلاثة أدوار لاحقة (منها واحد بعد إعادة تشغيل سطر) بقيت «يستعد» بلا ردّ حتى
  أوقفها المالك — فبدا أن إعادة التشغيل هي العلاج بينما العلاج كان عودة الشبكة (15:47).
- **الإصلاح** (بلا اعتماديات): `electron/neterror.js` مصنّف نقيّ بالنصّ (درس OBS-189) يُلحق
  `net {kind, code, message}` بأحداث `result` الخاطئة و`spawn_error` و`api_retry` في **قُمع
  `emit` المشترك في `main.js`** — فيشمل SDK وCodex وKimi ومحوّلات REST بسطر واحد، وبعد
  `acceptEvent` كي يحفظ سجل المحادثة الأصل. `agent.js` يطبّع `api_retry` (أرقام مُنقّاة ونصّ
  مقصوص) ويوسم خروج Query التابع لنتيجة خاطئة بـ`kind:'exit_after_result'` فلا يُرسم له
  صندوق ثانٍ. `electron/connectivity.js` مراقب يبدأ **بعد أول خطأ مصنَّف فقط** ويفحص حلّ
  الأسماء (`dns.lookup` لثلاثة مضيفين، لا `navigator.onLine` لأن محوّلات Hyper-V/VirtualBox
  «Up» دائماً) كل 5 ث حتى 20 دقيقة، ويبثّ `connectivity` عند الانقطاع مرة وعند العودة مع مدتها
  أو عند الاستسلام معلناً. الواجهة: سطر «يعيد الاتصال بالخادم (n/m)» يُحدَّث في مكانه، ورسالة
  عربية تقول السبب الحقيقي («انقطع الاتصال… تعذّر حلّ اسم الخادم… لا حاجة لإعادة تشغيل سطر»)،
  وإشعارات الانقطاع/العودة تدعو إلى «أعد المحاولة».
- **حدّ مُصرَّح به**: لا يعالج انقطاعاً يفوق ميزانية إعادة محاولة CLI؛ يجعل الحالة **مرئية
  وصادقة** ويُبقي المحادثة محفوظة. لم يُقَس حياً بقطع الشبكة فعلاً (الاختبار قطعي بمؤقّتات
  وبحث محقونين + حرس نصية على الوصلات الأربع).
