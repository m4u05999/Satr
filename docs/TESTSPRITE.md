# اختبار «سطر» عبر TestSprite

## تجربة الاستخدام المختصرة

عند ضبط مفتاح TestSprite يكفي أن يكتب المستخدم: «أريد اختبار». يتعرف «سطر» على نية الاختبار
من دون اشتراط أسماء أدوات MCP أو أوامر Terminal. إذا لم يحدد المستخدم النطاق، يطلب الوكيل مرة
واحدة اختيار الاختبار السريع للتعديلات، أو المشروع كاملاً، أو حالات محددة؛ ويسأل عن تسجيل الدخول
وسياسة التعامل مع الإخفاقات. الافتراضي الموصى به هو التقرير فقط بلا إصلاح تلقائي.

يبث «سطر» حالة التجهيز والتقدم والاكتمال في الواجهة. معيار الاكتمال هو تغير
`testsprite_tests/tmp/test_results.json` بعد خط الأساس ووصول كل الحالات المطلوبة إلى
`PASSED` أو `FAILED` أو `SKIPPED`؛ لا ينتظر خروج غلاف CLI إذا كان ملف النتائج قد اكتمل.

## ما الذي يمكن اختباره؟

«سطر» تطبيق Electron وليس موقعاً عادياً. لذلك الاختبار الكامل الصادق يتكوّن من طبقتين:

1. **TestSprite** يختبر واجهة Web عبر harness محلي على `http://127.0.0.1:4173/`. الـharness
   يحمّل ملفات `src/` الحقيقية ويحقن محاكاة خارجية لـ`window.satr`؛ لا يستعمل مفتاحاً أو نموذجاً
   حقيقياً، ولا يكتب إلى المشروع.
2. **الطقم الأصلي** يختبر Node وElectron وIPC وCSP والطرفية وغرفة العمليات عبر
   `npm run test:full`.

لا يجوز وصف TestSprite وحده بأنه E2E كامل لـElectron؛ الـharness لا يشغّل `main.js` أو
`preload.js` أو `node-pty` الحقيقي.

## الطريقة الأساسية: من دردشة «سطر»

أعد تشغيل «سطر» بعد تحديث الكود، اختر محرك Codex وجذر المشروع، ثم أرسل رسالة واحدة:

```text
اختبر مشروع «سطر» كاملاً باستخدام TestSprite. نفّذ TestSprite الفعلي ثم الطقم الأصلي،
ولا تصلح الإخفاقات ولا تعدّل كود الإنتاج ولا تنشئ commit.
```

يجمع «سطر» بقية العقد تلقائياً داخل الدور: يشغّل Web harness على `127.0.0.1:4173`، يحقن
المنفذ والمسار وتسلسل أدوات TestSprite في طلب Codex، ثم يوقف الخادم في نهاية الدور أو عند
الإيقاف/الفشل. تظهر استدعاءات TestSprite كبطاقات أدوات داخل المحادثة. عند وصول الدور إلى
`npm run test:full` قد يظهر مربع إذن لتنفيذ الأمر؛ وافق عليه ليكتمل الجزء الأصلي.

يُسمح لـTestSprite بإنشاء ملفاته داخل `.testsprite/` فقط. لا حاجة إلى فتح PowerShell أو إبقاء
خادم يدوي يعمل. التقرير النهائي يجب أن يفصل Web harness عن Electron/IPC/PTY الأصلي.

## التشخيص اليدوي الاحتياطي

لا تحتاج الخطوات التالية في المسار الطبيعي. استعملها فقط إذا تعذّر البدء التلقائي أو أردت عزل
مشكلة الخادم عن مشكلة حساب TestSprite.

### تحقق الجاهزية

```powershell
npm run test:testsprite-ready
```

يتحقق الأمر من عقد MCP، وحواجز خادم الـharness، ثم يقلع واجهة «سطر» الحقيقية داخل Chromium
ويرسل رسالة عبر mock مع صفر أخطاء CSP/console.

### تشغيل سطح TestSprite يدوياً

افتح PowerShell داخل جذر المشروع واتركه مفتوحاً:

```powershell
npm run testsprite:harness
```

النتيجة المتوقعة:

```text
TestSprite harness: http://127.0.0.1:4173
```

الخادم مربوط بـ`127.0.0.1` فقط، يخدم `src/` فقط، يرفض symlink/path traversal وطرق الكتابة،
ولا يقرأ `.env` أو خزنة مفاتيح «سطر».

### فحص اتصال الحساب

أعد تشغيل «سطر» بعد تحديث الكود، اختر محرك Codex، ثم أرسل:

```text
استخدم TestSprite الآن. استدعِ testsprite_check_account_info مرة واحدة فقط للتأكد من الاتصال.
لا تعرض البريد أو الخطة أو الرصيد؛ قل فقط «اتصال TestSprite ناجح» أو اذكر رمز الخطأ.
```

يجب أن تظهر بطاقة أداة باسم
`testsprite:testsprite_check_account_info`. ظهور `user rejected MCP tool call` يعني أن التطبيق
لم يُعد تشغيله على النسخة الجديدة.

### عقد الاختبار الكامل المحقون تلقائياً

لا يلزم إرسال النص التالي في المسار الطبيعي؛ «سطر» يبنيه آلياً. يُحفظ هنا مرجعاً للتشخيص
ومراجعة حدود التفويض:

```text
استخدم TestSprite لإجراء اختبار شامل وصادق لمشروع «سطر» الحالي.

تفويض هذا الدور: مسموح لك باستدعاء أدوات TestSprite المفعّلة، وإنشاء ملفات TestSprite داخل
`.testsprite/` فقط. لا تعدّل كود الإنتاج، لا تضف اعتماديات، ولا تنشئ commit.

سطح الويب الاختباري جاهز فعلاً على:
- localPort: 4173
- pathname: /
- type: frontend
- projectPath: D:\sater\satr-2
- testScope: codebase
- serverMode: development

نفّذ بالتسلسل ولا تستبدل TestSprite باختبارات npm:
1. استدعِ testsprite_check_account_info وتوقف إن فشل الاتصال.
2. يعتمد «سطر» حالة `testsprite_tests/tmp/config.json`: إن كانت التهيئة مكتملة فلا تستدعِ
   bootstrap. وإلا استدعِ testsprite_bootstrap مرة واحدة بالقيم الدقيقة أعلاه وانتظر حفظ نموذج
   الإعداد الأولي قبل المتابعة.
3. استدعِ testsprite_generate_code_summary.
4. استدعِ testsprite_generate_standardized_prd.
5. استدعِ testsprite_generate_frontend_test_plan مع needLogin=false.
6. استدعِ testsprite_generate_code_and_execute مع projectName="satr-2" وtestIds=[] و
   additionalInstruction="اختبر RTL والعربية، الإقلاع، الشريط العلوي، اختيار المحرك، المؤلف،
   إرسال الرسالة المزيّفة، الثيم، اللوحات، الطرفية المزيّفة، وعدم وجود console/CSP errors.
   لا تدّعِ اختبار Electron/IPC/PTY الحقيقي." وserverMode="development".
7. لا تفتح dashboard أو متصفحاً خارجياً. أعطني رابط/مسار التقرير ومعرّفات الحالات في المحادثة.
8. بعد انتهاء TestSprite شغّل `npm run test:full` للطقم الأصلي المكمل.

في التقرير افصل بوضوح بين:
- نتائج TestSprite على Web harness.
- نتائج Node/Electron الأصلية.
- الأجزاء غير المغطاة فعلياً.

ملفات `testsprite_tests/tmp/` مؤقتة ومستبعدة من Git. قد تكتب حزمة TestSprite مفتاح `API_KEY`
في config المؤقت أثناء التشغيل؛ ينقّيه «سطر» عند بدء الدور ونهايته، ولا يجوز نشر مجلد `tmp`.
اعرض Passed/Failed/Skipped، أول سبب جذري لكل فشل، و`git status --short`. لا تصلح أي فشل.
```

بعد اكتمال الاختبار أوقف الـharness في PowerShell عبر `Ctrl+C`.

## سياسة أذونات Codex

خادم TestSprite لا يُحقن إلا عندما تجمع رسالة المستخدم بين اسم TestSprite وفعل صريح مثل
«استخدم/اختبر». عندها تُعتمد قائمة ثابتة من أدوات الاختبار لذلك الدور فقط. أداة فتح dashboard
غير موجودة في القائمة، وأي أدوات تضيفها حزمة TestSprite مستقبلاً لا تعمل تلقائياً.
