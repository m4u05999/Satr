# خط أساس صقل حلقة المتصفح

**التاريخ:** 2026-07-22

## الهدف

قياس الكلفة الفعلية للقطات المعاينة والتفاعل مع DOM قبل اقتراح صقل بروتوكول
`browser_snapshot` و`browser_click` ومرجعيات العناصر.

## المنهج

- fixture محلي حتمي داخل عملية Electron قصيرة العمر.
- 81 عنصراً تفاعلياً ظاهراً.
- ثلاث لقطات `snapshot()` ونقرتان تعيدان بناء زر داخل DOM.
- محاولة واحدة بالمرجع القديم بعد إعادة البناء.
- خمس تشغيلات مستقلة، والنتائج الزمنية أدناه هي الوسيط.
- المرحلة الأولى استخدمت `electron/preview.js` مباشرةً لعزل كلفة DOM، ثم أُعيد السيناريو
  في المرحلة الثانية عبر Codex وناقل MCP الحقيقي بعد إصلاح الرفض الصامت.

في الوضع الضابط ينفّذ لقطة أولى ثم ست دورات `click→snapshot`. استُخدم Claude Haiku 4.5
كي تكون مقارنة 81/200 عنصر على النموذج نفسه:

نمو حجم اللقطة `2.44×` عند نمو العناصر `2.47×` يثبت أن كلفة النص خطية تقريباً في هذا

## الاستنتاجات

1. كلفة نقل MCP صغيرة: نحو 2–5 ms فوق تنفيذ `preview.js` المباشر في العمليات الدافئة.
2. كان انتظار رصد DOM الثابت يهيمن على زمن النقر؛ H3 خفّض وسيطه من 376.5ms إلى 5ms.
3. نص اللقطة لا يدخل خطياً سياق Codex Code Mode، لكنه ينمو خطياً ويعاد إلى Claude SDK؛
   لذلك تختلف أولوية H1 حسب المحرك.
4. H2 أزال التباس إعادة `e81` بربط كل ref بجيل، ثم جعل H1 الفهارس الجديدة متزايدة داخله.
5. H1 خفّض نتائج أدوات حلقة Claude 82.3% وعدد أدوارها 40%، دون دليل مالي كافٍ بعد.

## فرضيات قابلة للاختبار

### H1 — نتيجة DOM مختصرة بعد الفعل

قد تقلل نتيجة موجزة للعناصر المتغيرة الحاجة إلى لقطة كاملة بعد كل فعل.

**معيار القبول:** لا تتجاوز النتيجة 25% من حجم اللقطة الكاملة في fixture الحالي،
وتتضمن العنصر المتغير وحالة التنقل بلا فقد للمعلومة اللازمة للفعل التالي.

**النتيجة — مقبولة في 2026-07-22:** أصبح مراقب الأفعال يبني فرقاً دلالياً للعناصر
التفاعلية (`+` إضافة، `-` حذف، `~` تغيير)، ويمنح العناصر الجديدة refs متزايدة لا يعاد
استخدامها داخل جيل اللقطة. تُرتّب الإضافات أولاً كي تصل ref اللازمة للفعل التالي، ثم تُقص
الأسطر الكاملة عند الأصغر من `1600 bytes` أو `25%` من لقطة العناصر السابقة. إذا وقع القص
تقول النتيجة صراحةً إن لقطة كاملة لازمة للأجزاء غير المغطاة. التنقّل لا يعيد delta، واللقطة
التالية تبطل refs المولّدة كما في H2.

أعيد مسبار Claude نفسه على fixture ذي 200 عنصر في وضع delta: لقطة واحدة ثم ست نقرات،
وكل نقرة تستخرج ref التالية من نتيجة النقرة السابقة بلا CSS ولا لقطة وسيطة:

| المقياس | الضابط `snapshot` | بعد H1 `delta` | التغيّر |
|---|---:|---:|---:|
| اللقطات / النقرات | 7 / 6 | 1 / 6 | اللقطات -85.7% |
| أدوار SDK | 15 | 9 | -40.0% |
| مجموع نتائج الأدوات | 45,951 bytes | 8,121 bytes | -82.3% |
| وسيط نتيجة النقرة | 88 bytes | 272 bytes | يتضمن delta |
| مدة الدور | 35,738 ms | 36,389 ms | +1.8% |
| cache creation / read | 122,446 / 1,102,429 | 206,378 / 936,057 | توزيع مختلف |
| التكلفة المبلّغة | $0.3638429 | $0.5132267 | +41.1% في تشغيل واحد |

نجح العقد كاملاً: `1 snapshot` و`6 clicks` و`9 turns`، بلا إذن أو خطأ أو ref سيئة.
مجموع فئتي cache creation/read انخفض 6.7%، لكن الانتقال من cache read الأرخص إلى creation
الأغلى رفع التكلفة المبلّغة؛ لا تكفي عينة واحدة لعزو ذلك إلى H1 أو ادعاء وفر مالي. الأثر
المثبت هو خفض نقل نتائج الأدوات وعدد أدوار الحلقة. يثبت `test:preview-member-live` أيضاً
أن delta لا تتجاوز 25%، وأن ref الجديدة تعمل فوراً ثم تصبح `stale_ref` بعد لقطة جديدة.

#### إعادة قياس مزدوجة داخل نافذة cache

وُسّع المسبار ليشغّل ترتيباً متعاكساً `snapshot→delta` ثم `delta→snapshot` داخل عملية
Electron واحدة، مع حارس صارم لعدد الأدوات. اكتمل زوجان صالحان بالترتيبين، ثم أوقفت التجربة
بدلاً من حرق تكلفة إضافية عندما تكرر عدم التزام Haiku بالعدد. استُبعدت ثلاث محاولات ولم
تدخل الحساب: `5 snapshots/5 clicks`، ثم `7/7`، ثم `8 snapshots/6 clicks` مع ToolSearch
إضافية وخطأ أداة. هذا تذبذب في اتباع مهمة القياس، لا فشل في DOM delta.

| وسيط زوجين صالحين | `snapshot` | `delta` | التغيّر |
|---|---:|---:|---:|
| أدوار SDK | 15 | 9 | -40.0% |
| نتائج أدوات المتصفح | 47,792.5 bytes | 7,910 bytes | -83.45% |
| مدة الدور | 47,744.5 ms | 26,211 ms | -45.10% |
| التكلفة المبلّغة | $0.586728 | $0.474665 | -19.10% |
| cache creation | 194,966 | 201,843 | +3.53% |
| cache read | 1,863,430 | 627,774.5 | -66.31% |
| output tokens | 1,837 | 1,385.5 | -24.58% |

انخفضت التكلفة داخل كل زوج على حدة: **25.02%** عندما سبق snapshot، و**10.97%** عندما
سبقت delta. لذلك أصبحت فرضية الوفر المالي **مدعومة أولياً** بعد ضبط ترتيب cache، لكنها
ليست نتيجة نهائية إحصائياً لأن `n=2`. النتيجة الأقوى ما زالت انخفاض الأدوار والـbytes
والزمن في كلا الترتيبين. الارتفاع السابق 41.1% كان مقارنة غير مزدوجة، ويرجّح أنه تأثر
بحالة cache المختلفة؛ هذا تفسير مرجح لا إثبات سببي.

#### قياس Kimi ACP بالترتيب المتعاكس

أضيف `npm run test:browser-loop-kimi-probe` وشُغّل زوجان `snapshot→delta` ثم
`delta→snapshot` على K3 وfixture نفسه ذي 200 عنصر. كشف التشغيل الأول بوابة ACP خارجية
حول أدوات MCP المدمجة فوق بوابة سطر الداخلية؛ كانت تطلب إذناً حتى لـ
`mcp__satr__browser_snapshot`. أُصلح ذلك بقبول الغلاف فقط عندما يبدأ الاسم حرفياً بـ
`mcp__satr__` ويطابق أداة معروفة في خادم سطر الحالي. الاسم المجرد وأي خادم خارجي لا
يدخلان الاستثناء، وتبقى بوابة `codexmcp` الداخلية صاحبة قرار النطاق والفعل الحساس والميزانية.

بعد الإصلاح اكتملت التشغيلات الأربعة بلا إذن أو خطأ أو selector CSS. سجّل المسبار الـrefs
عند `preview.clickElement` نفسها: وضع snapshot استخدم أجيالاً متعاقبة، بينما استخدم وضع
delta السلاسل `s8:e200→s8:e205` و`s9:e200→s9:e205` بلا لقطة وسيطة.

| وسيط زوجي Kimi | `snapshot` | `delta` | التغيّر |
|---|---:|---:|---:|
| اللقطات / النقرات | 7 / 6 | 1 / 6 | اللقطات -85.71% |
| نتائج أدوات المتصفح | 47,407.5 bytes | 8,075 bytes | -82.97% |
| مدة الدور | 84,253 ms | 46,983 ms | -44.24% |
| التكلفة المبلّغة | غير معلنة | غير معلنة | لا يمكن القياس |

انخفض الزمن في الزوجين منفردين **45.26%** و**43.26%**، لذلك أثر H1 في تقليل الحلقة
عابر للمحركين Claude SDK وKimi ACP. لا يعيد ACP في عقد الدور الحالي tokens تفصيلية أو
تكلفة، فلا يوجد أساس لادعاء وفر مالي خاص بـKimi.

### H2 — مراجع مرتبطة بجيل اللقطة

ربط المرجع بجيل، مثل `s3:e1`، يمنع استخدام مرجع من لقطة سابقة على عنصر أعيد ربطه.

**معيار القبول:** أي مرجع من جيل سابق يعيد `stale_ref` ولا ينفذ فعلاً على DOM.

**النتيجة — مقبولة في 2026-07-22:** أصبحت المراجع بصيغة `s<generation>:e<index>`، والجيل
مرتبط بالـ`webContents` النشط ويُبطل عند لقطة جديدة أو تنقّل أو تبديل/إغلاق العرض. ترفض
كل أدوات العناصر الصيغة القديمة `eN` وأي جيل سابق بـ`stale_ref` مركزياً قبل `waitReady`
أو الوميض أو `executeJavaScript`. كما يرفض مسارا إذن Claude وCodex الإدخال القديم قبل
عرض مربع إذن، فلا يلمس DOM ولا يستهلك قرار المستخدم. يثبت `test:preview-member-live`
أن نفس العنصر يقبل ref الحالي ويرفض السابق بلا تغيير، ويثبت `test:codexmcp` الرفض قبل
الإذن والمعالج.

أعاد مسبار Codex الحي لخمس دورات refs متعاقبة (`s1:e81` ثم `s2:e81`…)، ورفض 5/5
محاولات قديمة بلا أذونات أو تشخيصات. بقي وسيط النقر الناجح **6ms** ووسيط `stale_ref`
**3ms**، ووسيط اللقطة **5ms**. زاد وسيط حجم اللقطة من 2,360 إلى 2,603 bytes (+10.3%)
بسبب بادئة الجيل، ومجموع نتائج MCP من 47,213 إلى 51,324 bytes (+8.7%)، بينما زاد input
من 36,218 إلى 36,400 رمزاً (+0.5%) فقط. أصبح المسبار نفسه حارساً يفشل إن لم تكن refs
جيلية، أو لم يفشل stale خمس مرات بالرسالة الصحيحة، أو ظهر إذن غير متوقع.

### H3 — انتظار تكيفي بعد النقر

يمكن إنهاء مراقبة التغير مبكراً عند رصد تغير متزامن بدلاً من انتظار ثابت.

**معيار القبول:** وسيط أقل من 200 ms للتغير المتزامن، مع بقاء كشف `dom_changed`
صحيحاً في اختبارات التغير المتأخر والتنقل.

**الحالة:** أولوية أولى؛ الوسيط الحي 376.5 ms، بينما بقية كلفة MCP بضعة ميلي ثوانٍ.

**النتيجة — مقبولة في 2026-07-22:** استُبدل انتظار `360ms` الثابت بـPromise داخل الصفحة
يوقظه `MutationObserver` عند أول تغير حقيقي أو تنقّل، مع حد `360ms` موازٍ في العملية
الرئيسية للأفعال بلا أثر أو الصفحات المخنوقة. انخفض وسيط النقر الناجح في مسبار الخمس
دورات من **376.5ms إلى 5ms** (تحسن 98.7%)، وبقي stale عند 3ms ونجح 5/5. انخفض زمن
الدور من 33,136ms إلى 29,462ms، قريباً من الوفر المتوقع لعشر نقرات. يثبت
`test:preview-member-live` التغير المتزامن تحت 200ms، والتغير المؤخر 120ms، وانتظار النافذة
الكاملة للفعل بلا أثر، والتنقّل؛ كما نجحت اختبارات المنصات والأسرار وسياسة النطاق و116 تحقق MCP.

### H4 — موثوقية ناقل MCP الحي

الرفض الفوري بلا بطاقة إذن يمنع قياس الحلقة الحقيقية ويبدو منفصلاً عن عقد MCP المحلي؛
`npm run test:codexmcp` نجح في 116 تحققاً.

**معيار القبول:** تعمل `list_background_tasks` القرائية بلا مربع إذن، ويعرض
`open_preview` مربع الإذن أو ينفذ وفق وضع التحكم بدلاً من رفض صامت.

**النتيجة — مقبولة في 2026-07-22:** كان Codex يضيف موافقة MCP خارجية بنموذج فارغ، وكان
`codex.js` يرفضه كنموذج غير مدعوم قبل بلوغ بوابة `codexmcp.js`. أصبح النموذج يُقبل تلقائياً
فقط عندما يطابق بصمة خادم `satr_preview` المدمج؛ الخوادم الخارجية والنماذج ذات الحقول تبقى
خارج الاستثناء. أثبت مسبار حي بالسياسة `default` نجاح `list_background_tasks` بلا إذن أو
تشخيص، وأثبت مسبار ثانٍ وصول `open_preview` الخارجي إلى `permission_request` الداخلي؛ رُفض
الإذن عمداً ولم يُفتح الموقع. نجحت أيضاً اختبارات `test:codex-contract` و`test:codexmcp`
و`test:browserorigin` و`test:autogate`.

### H5 — الزر العادي خارج النموذج

كشف المسبار أن `<button>` بلا `type` كان يُصنّف `submit` حتى خارج `<form>`، فيطلب إذناً
لكل نقرة رغم أن `localhost` موثوق ووضع التحكم مفعّل.

**النتيجة — مقبولة في 2026-07-22:** أصبح زر HTML الافتراضي حساساً كإرسال فقط عند ارتباطه
بنموذج؛ مفردات الأفعال الخطرة وبقية الحواجز لم تتغير. يثبت `test:browser-platform-live`
أن زر الإرسال عبر أصل خارجي يبقى حساساً والزر العادي خارجه لا يُصنّف إرسالاً.

## التجربة التالية

1. أُغلق H1 كتحسين مثبت للأدوار والـbytes والزمن عبر Claude SDK وKimi ACP.
2. إن لزم ادعاء مالي منشور، إعادة أزواج Claude بمنفّذ حتمي لا يعتمد على عدّ النموذج للأفعال.
