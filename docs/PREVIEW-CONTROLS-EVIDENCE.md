# إصلاح أزرار معاينة سطر — 2026-09-10

بلاغ المالك: زر الهاتف/العادي يغيّر حالته أحياناً بلا تغيير الصفحة، ولا يتعافى إلا بإغلاق المعاينة وفتحها. يشمل الطلب مراجعة بقية أزرار المتصفح بحثاً عن أعطال مماثلة.

## السبب والإصلاح

- يحتفظ electron/preview.js بمقاس browser_set_viewport في viewportOverride. كان زر الجهاز يرسل مستطيلاً جديداً، لكن المقاس المحفوظ يقيّده مجدداً؛ close وحدها كانت تمسحه. نقرة الجهاز الآن ترسل resetViewport=true مع المستطيل نفسه. القياسات التلقائية لا تلغي اختيار الوكيل؛ القصد يبقى مؤجلاً قبل إنشاء المعاينة وأثناء حجبها، ويُرسل حتى إذا لم تتغير أبعاد اللوحة الضيقة أو عادت ثلاث نقرات سريعة للوضع نفسه.
- يُنقّى resetViewport في main.js إلى القيمة المنطقية true حصراً، ويعبر دالة previewBounds المحددة في preload. لا قدرة عامة جديدة ولا تغيير في عزل الصفحة. يحافظ effectiveBounds على الحدود الصفرية أثناء الحجب حتى مع وجود مقاس محفوظ.
- محاكاة الشبكة تنتظر إقرار CDP وتُسلسل الطلبات لكل WebContents. يظهر الوضع المؤكد فقط، ويستعيد الزر قابليته للنقر في finally. لا تفصل العملية اتصال debugger مستعاراً، وتحرر اتصالها بعد أول فشل. قياس detach الحقيقي أثبت عودة الاتصال؛ فتح DevTools وحده لم يفصله في هذه البيئة.
- حدث closed يزيل حالات العرض القديم. إعادة التحميل تعيد إنشاء الصفحة، والردود المتأخرة لفتحها أو التنقل لا تعيد started لعرض مغلق. تُرشّح أحداث WebContents القديمة، وتُعاد أخطاء الأوامر بدلاً من نجاح صامت. مسح التخزين ينتظر الاكتمال قبل إعادة التحميل.
- إلغاء التحديد أو بدء تحديد جديد يبطل الرد السابق. زر إرسال العنصر يلتقط بياناته وعنوانه قبل انتظار الصورة؛ الإلغاء والإغلاق والتحديد الجديد تبطل الإرسال المتأخر، فلا يقرأ عنصراً محذوفاً أو يخلط صورة العنصر السابق بالجديد. يُمنع الإرسال المكرر أثناء الانتظار وتتحرر الأزرار بعد نهايته. فشل إعادة تشغيل الخادم يعيد تمكين زره أيضاً.

## الاختبارات والأدلة

- [حارس الواجهة](evidence/preview-controls/ui/README.md): واجهة الإنتاج كاملة داخل Chromium وحدود preload مضبوطة. شملت المراجعة الجهاز والتنقل ووحدة التحكم ودرج المزيد والتحديث التلقائي والشبكة والتحديد وإرسال العنصر وإعادة تمكين زر الخادم. ثماني عضّات فعلية محفوظة بأوامرها وعدّ الأنماط ورسائل الفشل والاستعادة؛ وحالات رد الفتح/التنقل ولقطة العنصر سقطت فعلياً على المصدر السابق قبل الإصلاح.
- [حارس العملية الرئيسية](evidence/preview-controls/backend-bite.md): 80 فحصاً و13 عضّة فعلية. يشغّل وحدة preview.js الإنتاجية مع حدود Electron مضبوطة. البصمة المسجلة للعضّات تسبق تصحيح تعليق DevTools فقط؛ لا اختلاف منطقي بسبب ذلك التصحيح.
- [التجارب الحية](evidence/preview-controls/live.md): ثلاث نوافذ مصدر معزولة، بلا حسابات من المالك أو أدوار مدفوعة أو تسجيل. ثبتت المقاسات 300→390→768→1110، والحجب 0×0 مع مقاس مفروض، والتنقل والرجوع والتقدم وإعادة التحميل والشبكة وإعادة إنشاء المتصفح. في التشخيص المستقل نجحت 12 نقرة متتابعة قبل فشل التنقل وبعده بقياس innerWidth الفعلي وإطارات الرسم، مع إبقاء نافذة الاختبار فوق النوافذ الأخرى.
- [الموضع البصري](evidence/preview-controls/rtl.json): فشل الحارس الأصلي أولاً في اللغتين لغياب العلامة من التقاط سطح المكتب (measured=null). أعيد الحارس نفسه دون تغيير حدوده، بمشغّل يبقي نافذته ظاهرة ومركزة فقط؛ نجحت المواضع الثلاثة في ar والثلاثة في en-US، وتطابق الموضع والعرض المطلوبان تماماً. لم يُغيّر إعداد ظهور نوافذ المنتج.

## حدود النتيجة

رُصدت حالة عابرة بعد التنقل الفاشل: حدود العرض تغيرت، لكن الصفحة أصبحت hidden وframes=0 ولم يتقارب innerWidth خلال 8 ثوانٍ. تعافت لاحقاً دون إغلاق العرض، ولم تتكرر في التشخيص المضبوط. لم يُحسم سببها؛ لا ننسبها يقيناً إلى حجب Windows أو DevTools، ولا ندّعي زوال كل حالة تجمد ممكنة. هذه مختلفة عن استمرار viewportOverride المؤكد والمصحح. كما أعادت أداة setViewport في المحاولة الأولى actual قديماً بعد انتظارها الحالي القصير؛ بقي هذا الحد موثقاً دون تغيير API الأداة في هذه الدفعة.

التجربة الحية سبقت إضافة حماية إرسال العنصر الأخيرة؛ دليلها هو حارس الواجهة قبل الإصلاح وبعده. لم تُجرَّب الكاميرا أو الميكروفون أو التسجيل الحقيقي أو مسح تخزين حساب المالك. لم يُغيَّر CSS في هذه الدفعة ولا تُدّعى شهادة شاملة لاتجاه العربية داخل Shadow DOM.

أُغلقت نوافذ التجارب الثلاث وخوادمها وطرفياتها. بقيت الأدلة وخط الأساس في dist/preview-controls-baseline والبناء؛ تعديلات المالك والمهام السابقة محفوظة. لا commit أو نشر أو ترقية اعتماديات.
