# محرك Codex في «سطر»

## نظرة عامة

محرك Codex في `electron/codex.js` محرك أصيل موازٍ لمحرك Claude، وليس محوّلاً لخرج سطر الأوامر. يشغّل ثنائي Codex المثبّت على الجهاز بالأمر `codex app-server`، ثم يتبادل معه رسائل JSON-RPC 2.0 ثنائية الاتجاه عبر `stdin` و`stdout`، برسالة JSON واحدة في كل سطر.

يتيح هذا الاتصال لـ«سطر» استقبال البث والأحداث، واعتراض طلبات الإذن والرد عليها، ثم تطبيع خرج Codex إلى عقد الأحداث المشترك في الواجهة. لا يُحزَّم ثنائي Codex مع التطبيق؛ يُبحث عنه عبر `CODEX_BIN`، أو تثبيت npm العالمي، أو امتداد OpenAI في VS Code، أو `PATH`.

## دورة التشغيل

1. يرسل المحرك `initialize` إلى `app-server`.
2. يبدأ خيطاً عبر `thread/start`، أو يستأنف جلسة محفوظة عبر `thread/resume`. إذا فشل الاستئناف يبدأ خيطاً جديداً.
3. يبدأ الدور عبر `turn/start`، ويمرّر المهارات المفعّلة كمدخلات أصلية
   `{type:'skill', name, path}` ثم النص والصور والنموذج المختار. ثُبّت العقد من JSON Schema
   الذي يولّده `codex app-server 0.144.1 generate-json-schema --experimental`.
4. يستقبل إشعارات v2 من عائلات `thread/*` و`turn/*` و`item/*`، ويتجاهل قناة `codex/event/*` القديمة.
5. عند اكتمال الدور يصدر النتيجة، يغلق `stdin`، ويمهل الخادم قليلاً لحفظ الجلسة قبل إنهاء العملية.

تُقرأ المصادقة من إعداد Codex نفسه، عادةً من `~/.codex/auth.json` لتسجيل اشتراك ChatGPT أو مفتاح API. لا يحقن «سطر» بيانات الاعتماد في العملية ولا يعيد قيمها إلى الواجهة.

## أوضاع الصلاحيات

| وضع «سطر» | `approvalPolicy` | صندوق الرمل | السلوك |
|---|---|---|---|
| `default` | `on-request` | `workspace-write` | يسأل قبل الأوامر وتعديلات الملفات. |
| `acceptEdits` | `on-request` | `workspace-write` | يقبل `apply_patch` تلقائياً، ويستمر في السؤال قبل الأوامر. |
| `plan` | `on-request` | `read-only` | يسمح بالتحليل والتخطيط من دون الكتابة. |
| `bypassPermissions` | `never` | `danger-full-access` | يعمل بلا أسئلة وبلا صندوق رمل؛ وهو وضع عالي الخطورة. |

القيمة `never` تعني «لا تصعّد لطلب إذن»، ولا تعني «اقبل تلقائياً». لذلك لا تُستخدم للقبول التلقائي مع صندوق قراءة فقط. قرارات بروتوكول v2 هي `accept` و`acceptForSession` و`decline` و`cancel`. كما قد يحمل طلب الخادم المعرّف `id = 0`، لذا يُعامل أي `id` غير فارغ بوصفه صالحاً.

## أهم الأحداث

### أحداث Codex الواردة

- `thread/started`: يثبّت معرّف الجلسة.
- `item/agentMessage/delta`: يبث أجزاء نص المساعد.
- `item/started`: يلتقط حالة الملفات قبل تعديلها لدعم الفرق والتراجع.
- `turn/plan/updated`: يعرض أول نسخة من خطة المهام.
- `item/completed`: يحوّل رسائل المساعد، وتنفيذ الأوامر، وتغييرات الملفات، وملخصات التفكير.
- `turn/completed` و`turn/failed`: ينهيان الدور بنتيجة نجاح أو خطأ.
- `item/commandExecution/requestApproval` و`item/fileChange/requestApproval`: يطلبان إذن تنفيذ أمر أو تعديل ملف.

### أحداث «سطر» الناتجة

يطبع المحرك الأحداث إلى الأنواع المشتركة: `system`، و`stream_text`، و`assistant`، و`user`، و`permission_request`، و`file_edit`، و`result`، إضافةً إلى `stderr` و`spawn_error` و`proc_done`. وبذلك لا تحتاج الواجهة إلى منطق خاص ببروتوكول Codex.

## النماذج المدعومة

تعرض «سطر» النماذج الحديثة فقط:

- `gpt-5.6-sol`
- `gpt-5.6-terra`
- `gpt-5.6-luna`
- `gpt-5.5`

يتطلب توفر النموذج دعمه في إصدار Codex CLI المثبّت وفي حساب المستخدم أو خطته؛ وقد يفشل الدور برسالة واضحة إذا لم يكن النموذج متاحاً.

## الحدود الحالية

- يعتمد المحرك على وجود Codex CLI مثبتاً ومسجلاً للدخول؛ لا يضم التطبيق الثنائي أو بيانات الاعتماد.
- يعتمد على أحداث v2، ولا يعالج قناة الأحداث القديمة `codex/event/*`.
- اختيار المهارات يرفق المهارات المفعّلة صراحةً بالدور ولا يكتب إعداد Codex العام؛ وهو
  توجيه سياق لا sandbox للملفات، لذلك تبقى حدود الثقة والأذونات مسؤولية صندوق الرمل.
- لا تُعرض كل إشعارات الخادم؛ تُهمل حالياً تفاصيل مثل حدود المعدّل، واستهلاك الرموز، وبدء MCP.
- قيمة التكلفة في حدث النتيجة هي `null`؛ المحرك يحسب مدة الدور فقط.
- عناصر مثل Web Search لا تحصل على بطاقة أداة مستقلة؛ يُكتفى بنص الوكيل.
- عرض الفرق والتراجع محدودان بالملفات حتى 2 MiB، وتُحتفظ بآخر 40 لقطة تعديل فقط.
- الموافقة «دائماً» محفوظة في ذاكرة عملية التطبيق، وليست إعداداً دائماً على القرص.
- وضع `bypassPermissions` يلغي الأسئلة وصندوق الرمل، لذا يجب استخدامه فقط في بيئة موثوقة.
