## أساس الحساب وStripe — 2026-09-20

اكتملت وحدتا Stripe الخادميتان في الخاص مع 30/30 اختباراً محلياً وعضتين مثبتتين واستعادة المصدر. المواصفة [83](internals/83-pro-accounts-sandbox.md) والاستئناف [§32](internals/82-pro-saved-tasks-v1.md). لا حسابات برو أو تسجيل دخول أو مخطط حسابات أو استحقاق مفعل أو ربط Stripe حقيقي بعد. أكد المالك أن مفتاحه يبدأ sk_live؛ لم يدخل أو يستخدم. أجّل Stripe إلى غد واعتمد Supabase المُدار مع Google للدخول. مشروع Supabase جاهز للقراءة عبر الموصل؛ إعداد Google ومضيف خادم برو والربط بالحسابات لم يكتمل بعد؛ نقطة الاستئناف الأخيرة في83. لا تغيير للأسعار أو Enterprise أو المثبت؛ لا Live أو نشر.

تعثر إعداد Supabase سابقاً بعد كشف أدوات القراءة رموز OAuth في عنوان العودة. سحب تفويض GitHub مثبت، وإبطال جلسة Supabase المستقلة غير مثبت. رقعة المصدر تجتاز 42 و189 فحصاً مع عضّة؛ لا تحديث للمثبت؛ أنشأ المالك لاحقاً مشروع التطوير بنفسه كما في نتيجة الربط أدناه. تفاصيل المتابعة وحدود الحجب في آخر [83](internals/83-pro-accounts-sandbox.md).

جهز Supabase CLI 2.117.0 لكن دخوله فشل عند قراءة profile. ترك المالك مشروع test القديم المتوقف، وأنشأ satr-pro-dev وربطه بموصل سطر للقراءة. نجح inspect بحالة ACTIVE_HEALTHY في ap-northeast-2، ونجحت قراءة قائمة 39 جدولاً مع truncated=false. هذا ربط تطوير مثبت، وليس Google Auth لمستخدمي برو أو تطبيق مخطط حسابات؛ التالي إعداد Google والتحقق من إعدادات الأمان. تفاصيل القياس في آخر83.

## 1. تحليل SWOT

### القوة
1. موقع بلا منافس: التطبيق العربي الوحيد بحلقة كاملة — بناء ⇒ بوابات مراجعة (غرفة
   العمليات) ⇒ إعلان (الاستوديو) ⇒ نشر. المنافسون يبيعون محرراً؛ سطر يبيع رحلة
   فكرة-إلى-منتج.
2. بنية جاهزة (§0 أعلاه) + كلفة وحدات مقيسة فعلياً.
3. بوابات الجودة تقلل «الوكيل خرّب مشروعي» — أكبر أسباب إلغاء الاشتراك في الفئة.
4. جاهزية تجارية فورية: سجل تجاري + بوابة محلية = تسعير بالريال ومدى وApple Pay؛
   لا منافس أجنبي يجاريها. والريال مربوط بالدولار فلا مخاطرة صرف مع كلفة المزودين.
5. النواة المجانية تبقي القمع واسعاً وتبني الثقة.

### الضعف
1. لا خادم اليوم: الاشتراك يستلزم أول backend (حسابات + بروكسي مفاتيح + فوترة) —
   سطح هجوم جديد وعبء تشغيل دائم على شخص واحد.
2. المحركات الرائدة خارج الصفقة: اشتراكات Claude Code/Codex/Kimi Code **لا يجوز
   إعادة بيعها** — الباقة تغطي محوّلات API والتوليد فقط، والتسويق يلتزم الصدق هنا.
3. ويندوز فقط حالياً — يضيّق السوق والمشترك يتوقع تعدد أجهزة.
4. قاعدة مستخدمين وليدة — تجارب التسعير على عيّنة صغيرة.

### الفرص
1. **احتكاك الدفع الإقليمي هو الخندق**: بطاقات كثير من الدول العربية مرفوضة عند
   OpenAI/Anthropic — «اشتراك بالريال يشغّل كل شيء» يحوّل المستبعَدين من السوق إلى
   عملاء. فتح سوق، لا ميزة.
2. غير المطورين العرب (طالب/صاحب متجر): «فكرة ⇒ موقع حي + فيديو إعلاني» — لا أحد
   يخدمهم بالعربية، واستعدادهم للدفع أعلى (يشترون الإمكان لا الراحة).
3. السياق السعودي: رقمنة المنشآت الصغيرة + طريق مؤسسي لاحق (satr-enterprise).
4. الباقة أكبر من إعادة بيع نماذج: النشر + الاستوديو + التوليد workflow يصعب هجره؛
   إعادة البيع وحدها سلعة تُسحق هوامشها.

### التهديدات
1. **انفجار الهامش**: الوكلاء يحرقون رموزاً بلا سقف متوقع؛ كل «غير محدود» بسعر ثابت
   انكسر (درس Cursor). العلاج بنيوي: **رصيد، لا unlimited — قاعدة غير قابلة للتفاوض**.
2. تقلب المنبع: تغيير أسعار/سياسات مزوّد يضغط الهامش فجأة.
3. إساءة الاستخدام: بروكسي مدفوع = مزارع مفاتيح؛ استضافة تحت العلامة = تصيّد
   ومحتوى مسيء يستلزم آلية إزالة من اليوم الأول.
4. نافذة زمنية: الكبار سيحسّنون RTL يوماً — التميز الدائم هو الحلقة الكاملة والدفع
   المحلي، لا العربية وحدها.

- الغاية النهائية تبقى: قياس الاستعداد للدفع بأموال حقيقية لا استبيان — التسجيل
  بالبريد إشارة أضعف ومرحلة عبور فقط.
- **نقطة قتل**: عدد حجوزات غير مقنع خلال شهر من تفعيل الدفع ⇒ السعر أو السرد خاطئ —
  يُعدَّل قبل بناء أي خادم.

### المرحلة 1 — الأساس المدفوع (4–6 أسابيع)
- أول خادم سطر: حسابات بسيطة (بريد + OTP) ⇒ **بروكسي مفاتيح** (المفتاح الرئيسي لا
  يغادر الخادم أبداً؛ **صفر تسجيل برومبتات** — عقيدة «بياناتك محلية» تبقى صادقة) ⇒
  ربط البوابة بالتجديد الشهري (توكن) ⇒ حدود استهلاك لكل حساب.
- التفعيل في التطبيق عبر نقاط ربط features.js القائمة: م٣ (توليد مدار) + مفاتيح
  المحوّلات المدارة. **سقوط دائم إلى BYOK عند نفاد الرصيد — المشترك لا يُحبس أبداً.**

### المرحلة 2 — النشر (الموجة الثانية)
- أولاً: زر نشر بحساب المستخدم نفسه (Cloudflare Pages / Netlify عبر OAuth واحد) —
  صفر مسؤولية محتوى وقيمة فورية.
- لاحقاً: نطاقات سطر الفرعية (`*.satr.site`) بحدود صارمة وآلية إبلاغ/إزالة **جاهزة
  قبل أول موقع منشور** — لا تُفتح قبل نضوج أرقام المرحلة 1.

### المرحلة 3 — التوسع
- خطة فرق/مؤسسات (بنية satr-enterprise جاهزة).
- النظر في وسيط تجميع نماذج (نمط OpenRouter) بدل عقود مباشرة مع كل مزود — تكامل
  واحد يفتح عشرات النماذج ويقلل مخاطرة المنبع.

## 3. قرارات محسومة وقيود صلبة

- **البوابة**: الاختيار مؤجل بقرار محمد (ميسر أو هايبر باي — كلاهما يعمل مع سجله
  التجاري؛ ترشيح سطر يبقى ميسر للانطلاق). التطوير لا يعلق على القرار: طبقة الدفع
  تُبنى بنمط سجل المحوّلات (عقد موحد: اشتراك/تجديد/إلغاء) والبوابة ملف تنفيذ
  قابل للتبديل، مع مسار «تفعيل يدوي» للمؤسسين قبل أي بوابة.
- **رصيد لا unlimited** — في كل خطة وكل تسويق.
- لا إعادة بيع لاشتراكات المحركات الأصيلة (Claude Code/Codex/Kimi Code) — تبقى
  بتسجيل دخول المستخدم.
- صفر تسجيل برومبتات في البروكسي، والنواة المجانية BYOK لا تُضعف لدفع الناس للاشتراك.
- **فرضية السعر للمرحلة 0**: خطة واحدة ~49 ر.س/شهر برصيد كلفته الفعلية ~20–25 ر.س
  (بالأسعار المقيسة: مئات الصور أو عشرات الفيديوهات أو ملايين رموز النماذج المفتوحة).
  فرضية تُختبر في المرحلة 0 لا حقيقة.

## 3ب. بند صيانة مجدول — ترقية Electron (بعد المرحلة 0)

- الحالة: المشروع مثبّت على Electron ‏^33 **عمداً** (prebuilds ‏node-pty تعمل تحته
  بلا إعادة بناء — `npmRebuild:false` وجهاز التطوير بلا Visual Studio)، لكن 33 خرج
  من نافذة الدعم الأمني الرسمية (آخر 3 نسخ كبرى).
- الشكل: جولة مستقلة صغيرة بعد المرحلة 0 — رفع الإصدار ⇒ التحقق من توافق prebuilds
  ‏node-pty مع ABI الجديد (العائق الحقيقي الوحيد) ⇒ `test:full` كاملاً ⇒ إصدار.
  لا ترقية عابرة داخل عمل آخر.
- تذكير تشغيلي (تشخيص 2026-08-10): شاشة ترحيب Electron الافتراضية = تشغيل بلا تطبيق
  (نقر مزدوج على electron.exe أو مجلد خاطئ) لا عطب تثبيت؛ التشغيل الصحيح `npm start`
  من جذر المشروع، والإصلاح `npm ci` بعد حذف node_modules، ولا Electron عالمي ولا
  `npm rebuild` أبداً.
