# معيار الإنجاز — Definition of Done

> هذا المستند يحدّد الحدّ الأدنى الذي يجب تحقّقه قبل إغلاق أي مهمة في مشروع «سطر».
> يكمّل `AGENTS.md` ولا يُلغيه؛ عند التعارض يكون `AGENTS.md` هو المرجع الأعلى.

---

## 1. الهدف والنطاق

**الهدف**: ضمان أن كل تغيير ينتقل من «تم التنفيذ على الجهاز» إلى «محمول وموثّق وقابل للمراجعة».

**النطاق**: ينطبق المعيار على:

- تغييرات الكود في `electron/` و`src/` و`scripts/`.
- تغييرات التوثيق في `docs/`.
- تغييرات عقود IPC أو الأحداث أو محركات الوكيل.
- تغييرات الواجهة العربية، بما فيها RTL/BiDi والوضعين الفاتح والداكن.

**خارج النطاق**: المهام البحثية الخالصة التي لا تُحدِث ملفاً تنفيذياً؛ ومع ذلك يجب أن تُنتج وثيقة أو ملاحظة محفوظة في `docs/` أو `AGENTS.md`.

---

## 2. التمييز بين المصطلحات

### Acceptance Criteria

شروط خاصة بالمهمة الحالية. تجيب على السؤال: **ما الذي يجب أن يفعله هذا التغيير؟**

مثال: «يكون زر الإذن ظاهراً عندما يطلب المحرك إذناً جديداً».

### Definition of Done

معيار عام ينطبق على كل مهمة. يجيب على السؤال: **متى نعتبر المهمة جاهزة للدمج؟**

يتضمّن التحقق والتوثيق والأدلة والمراجعة الأمنية.

### Verification Evidence

دليل ملموس يُراجع لاحقاً. يجب أن يحتوي على الأمر المشغّل ورمز الخروج والتوقيت والإصدار وBase commit وحالة الشجرة.

### Reported Result

ما أفاد به المنفذ شفوياً أو في سجل غير محفوظ. ليس دليلاً حتى يُحفظ بصورة دائمة وقابلة للمراجعة.

---

## 3. الحقول المطلوبة لكل تذكرة

قبل بدء التنفيذ يجب أن تكون المهمة واضحة فيما يلي:

1. **الهدف**: ما المشكلة أو الفرصة؟
2. **السلوك المتوقع**: كيف يعمل التغيير بعد الإنجاز؟
3. **خارج النطاق**: ما الذي لن يُغطّى في هذه المهمة؟
4. **الاعتماديات**: أي مهام أو قرارات تسبق هذه المهمة؟
5. **الملفات أو العقود المتأثرة**: `main.js`، `preload.js`، واجهة المستخدم، عقد IPC، إلخ.
6. **المخاطر الأمنية**: هل يُدخل التغيير مدخلات جديدة إلى `spawn` أو يكشف قدرات جديدة عبر preload؟
7. **معايير القبول القابلة للرصد**: شروط يمكن اختبارها بـ نعم/لا.
8. **خطة الاختبار**: أي اختبارات ستُشغّل، وهل هي قطعية أم حية؟
9. **دليل الإنجاز**: ماذا سيُسجّل كـ Verification Evidence؟

---

## 4. مستويات التحقق

يُطبّق التحقق على مستويات متدرجة حسب طبيعة التغيير:

| المستوى | متى يُستخدم | أمثلة |
|---|---|---|
| فحص بنائي | أي تعديل في JavaScript | `node --check` للملف المعدّل |
| اختبار مستهدف | تغيير منطقي في وحدة معيّنة | `npm run test:xxxxx` |
| اختبار تكامل | تغيير يمسّ أكثر من وحدة | `npm run test:integration` |
| اختبار حي Electron | تغيير واجهة أو IPC أو renderer | `npm run test:xxxx-live` |
| `test:full` | قبل اعتبار المهمة جاهزة | `npm run test:full:evidence` |
| اختبار الحزمة والمثبت | عند الإصدار | `npm run dist:dir` ثم فحص `dist/win-unpacked/` |

ملاحظة: لا يُعتمد على `test:full` وحده دون اختبار مستهدف يرتبط بالتغيير.

---

## 5. متطلبات تغييرات IPC

عند تغيير عقد IPC:

1. يُحدَّث `electron/main.js` لمعالجة الحدث الجديد والتحقق من مدخلاته.
2. يُحدَّث `electron/preload.js` ليكشف دالة محددة فقط عبر `window.satr`.
3. يُحدَّث كود الواجهة في `src/ui/` لاستخدام العقد الجديد.
4. يُحدَّث التوثيق في `CLAUDE.md` أو `docs/`.

قيود أمنية صلبة:

- لا تكشف `ipcRenderer` كاملاً.
- لا تُفعل `nodeIntegration`.
- لا تُعطّل `contextIsolation` أو `sandbox`.
- كل مدخل إلى `spawn` أو مسار يمرّ على regex صارم.

---

## 6. متطلبات تغييرات الواجهة

عند تغيير أي عنصر مرئي أو تفاعلي:

1. **العربية أولاً**: النصوص الظاهرة بالعربية.
2. **RTL/BiDi**: استخدام `dir="rtl"` على الحاويات و`dir="auto"` أو `unicode-bidi: plaintext` للنص المختلط.
3. **LTR للكود والمسارات**: الأكواد والمسارات والأرقام التقنية `direction: ltr`.
4. **الوضعان الفاتح والداكن**: كل لون عبر متغيّر Token في `src/styles/base.css`.
5. **CSP**: لا `<style>`/`<script>` مضمّن ولا سمات `style=`/`onclick=`؛ أنماط المكوّنات عبر `adoptedStyleSheets`.
6. **لقطة أو تحقق حي**: عند تغيير بصري يجب أن يكون هناك دليل بصري أو تشغيل حي تحت CSP.

---

## 7. متطلبات الأدلة

يجب أن يتضمّن Verification Evidence ما يلي:

- الأمر الكامل الذي شُغّل.
- رمز الخروج.
- توقيت التشغيل (UTC).
- إصدار التطبيق (`package.json`).
- Base commit من `git rev-parse HEAD`.
- حالة الشجرة من `git status --porcelain`.
- مسار الأثر الناتج (log أو JSON أو لقطة).

مثال:

```
command: npm run test:full:evidence
exit_code: 0
started_at: <timestamp>
app_version: <app-version>
base_commit: <base-commit>
working_tree_dirty: <true|false>
artifact: dist/test-runs/<timestamp>/summary.json
```

---

## 8. سياسة الشجرة المتسخة

- `base_commit` يمثل نقطة البداية فقط.
- `base_commit` لا يمثل الملفات غير الملتزم بها.
- يجب تسجيل `git status` كجزء من الأدلة.
- لا يجوز الادعاء بأن الاختبار يعود إلى commit وحده عند وجود تعديلات غير ملتزمة.
- إذا كانت المهمة تتطلب شجرة نظيفة، يُدرج ذلك في معايير القبول مسبقاً.

---

## 9. تصنيف النتائج

### Verified Evidence

نتيجة مؤكدة بأثر محفوظ: ملف log أو JSON أو لقطة، يتضمّن الأمر ورمز الخروج والتوقيت.

### Reported Pass

ما أفاد به المنفذ من نجاح دون أثر محفوظ. يُستخدم كملاحظة فقط ولا يُغلق به.

### Not Run

الاختبار لم يُشغّل. يُسجَّل بوضوح ولا يُحتسب نجاحاً.

### Blocked

تعذّر التشغيل بسبب عائق خارجي. يُحتاج إلى قرار صريح قبل الإغلاق أو التجاوز.

---

## 10. قواعد إغلاق المهمة

لا تُغلق مهمة إلا إذا تحقق ما يلي:

1. لا توضع معايير القبول المستقبلية داخل evidence.
2. لا توضع نتيجة ناجحة دون أثر أو سجل.
3. لا تُغلق مهمة بسبب نجاح اختبار غير مرتبط بها.
4. كل تغيير IPC مغطى باختبار أو مراجعة يدوية موثّقة.
5. كل تغيير واجهة مرفق بلقطة أو تحقق حي.
6. لا توجد ملفات جديدة خارج النطاق.

---

## 11. سياسة الفشل

1. أصلح فقط الفشل المرتبط بالتغيير.
2. إن واجهت عطلاً سابقاً أو غير مرتبط، سجّله بوضوح.
3. لا تُخفِ فشل مجموعة داخل ملخص نجاح عام.
4. إذا تكرر نفس الفشل لثلاث دورات متتالية، أوقف وأبلّغ عنه كعائق.
5. لا تُغيّر سلوك `test:full` لتجاوز فشل.

---

## 12. قائمة تحقق قابلة للنسخ

```markdown
- [ ] الهدف والسلوك المتوقع واضحان.
- [ ] خارج النطاق محدّد.
- [ ] الاعتماديات مكتملة.
- [ ] `node --check` للملفات المعدّلة.
- [ ] الاختبار المستهدف تم تشغيله ونجح.
- [ ] `test:full` تم تشغيله مع حفظ الأدلة.
- [ ] لا يوجد `git reset --hard` أو أوامر خطرة.
- [ ] لا توجد أسرار في السجلات.
- [ ] `contextIsolation` و`sandbox` مفعّلان.
- [ ] لا `nodeIntegration` ولا كشف كامل لـ `ipcRenderer`.
- [ ] النصوص العربية والمسارات LTR صحيحة.
- [ ] الألوان عبر Tokens.
- [ ] التوثيق محدّث.
- [ ] الأدلة المحفوظة تتضمّن الأمر ورمز الخروج والتوقيت والـ commit.
- [ ] حالة الشجرة مسجّلة.
```
