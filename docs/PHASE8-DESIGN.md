# المرحلة 8 — الطرفية العربية المدمجة (BiDi Terminal): بحث وتصميم

> وثيقة المرحلة 8.0 — بحث وتصميم فقط، **بلا كود**. أُنجزت ببحث ويب حيّ (يوليو 2026)
> لا بالاعتماد على الذاكرة. المراجع في آخر الوثيقة.

## 1. لماذا هذه المرحلة هي الخندق التنافسي

«سطر» اليوم يحل مشكلة العربية لمحادثة Claude Code فقط. لكن المشكلة الجذرية أوسع:
**لا توجد طرفية حقيقية على ويندوز تعرض العربية عرضاً صحيحاً** — لا Windows Terminal ولا
VS Code ولا أي طرفية مبنية على xterm.js. العربية تظهر مقطّعة الحروف ومعكوسة الاتجاه في
كلها. حتى Claude Code نفسه لديه قضية مفتوحة عن ذلك
([anthropics/claude-code#38656](https://github.com/anthropics/claude-code/issues/38656)).

الطرفيات الوحيدة التي تدعم BiDi فعلياً هي على لينكس فقط: **mlterm** و**Konsole** و**VTE**
(طرفية GNOME، طبّقت مواصفة BiDi منذ 2019). على ويندوز — بيئة مستخدمينا الأساسية —
الساحة فارغة تماماً. طرفية عربية مدمجة في «سطر» تحوّله من «واجهة لـ Claude Code» إلى
**أول طرفية عربية حقيقية**، وهذا لا يستطيع أحد نسخه بسرعة لأن الحل يتطلب الجمع بين
محرك طرفية ومحرك عرض BiDi — وهو بالضبط ما يمتلكه «سطر» (متصفح Chromium يعرض العربية
مجاناً وبكمال).

## 2. الحالة الراهنة للمكوّنات (نتائج البحث الحيّ)

### 2.1 xterm.js — لا دعم BiDi، ولن يأتي قريباً

- القضية [xtermjs/xterm.js#701](https://github.com/xtermjs/xterm.js/issues/701)
  «Support RTL languages» مفتوحة منذ **يونيو 2017** وما تزال مفتوحة في 2026، بوسوم
  `help wanted` بلا مكلَّف ولا PR مرتبط. xterm.js لا يشحن خوارزمية Unicode BiDi ولا
  جداول تشكيل الحروف العربية (letter joining/shaping) إطلاقاً.
- قضايا VS Code الحديثة (2025–2026) تؤكد استمرار المشكلة في أحدث الإصدارات:
  [microsoft/vscode#271615](https://github.com/microsoft/vscode/issues/271615) و
  [microsoft/vscode#296495](https://github.com/microsoft/vscode/issues/296495).
- العوائق التي ذكرها المشرفون: نموذج التحديد (selection) يفترض تطابق العمود المنطقي
  بالبصري واحداً لواحد، وموضع المؤشر، وإعادة التدفق (reflow)، وتفاعل RTL مع الأرقام
  والترقيم. أي حل BiDi يمس قلب المعمارية.
- **المُنقذ**: xterm.js يكشف **Buffer API عاماً وموثّقاً** (`term.buffer.active.getLine(i)`
  مع سمات الخلايا)، وحدث تبديل الشاشة البديلة (`buffer.onBufferChange`)، وتوجد نسخة
  `@xterm/headless` تعمل كمحلّل VT/ANSI كامل بلا DOM. أي أنه يمكن استعمال xterm.js
  **كمحرك حالة** (محلّل ANSI + شبكة خلايا + شاشة بديلة) مع عرضٍ نبنيه نحن.

### 2.2 مواصفة BiDi للطرفيات (freedesktop terminal-wg)

توجد [مواصفة رسمية لـ BiDi في محاكيات الطرفيات](https://terminal-wg.pages.freedesktop.org/bidi/)
(كتبها مطوّر VTE وطبّقتها VTE). قراراتها التصميمية تهمنا مباشرة:

- **BiDi عرضٌ فقط (display-only)**: المخزن المنطقي للشبكة لا يتغيّر؛ إعادة الترتيب تحدث
  عند الرسم فقط. (هذا يطابق نهجنا: شبكة xterm.js تبقى منطقية، والعرض HTML يعيد الترتيب.)
- **الوضع الضمني (implicit) هو الافتراضي**: خوارزمية Unicode BiDi تُطبَّق على كل سطر مع
  استنتاج اتجاه الفقرة تلقائياً — وهذا بالضبط ما يفعله المتصفح عبر
  `unicode-bidi: plaintext`، أي أن Chromium ينفّذ لنا الجزء الأصعب مجاناً.
- «المؤشر الملعون» (the cursed cursor): موضع المؤشر يبقى **منطقياً** وترجمته للبصري
  هي مسؤولية العارض — أصعب جزء في أي تنفيذ، ومُوثَّق كذلك.

### 2.3 node-pty — ناضج على ويندوز، لكنه اعتمادية أصلية

- الحزمة الرسمية [microsoft/node-pty](https://github.com/microsoft/node-pty) (يستخدمها
  VS Code نفسه): المستقر **1.1.0**، وسلسلة **1.2.0-beta** نشطة في 2026 (آخرها يونيو 2026)
  مع تحديثات ConPTY مستمرة.
- **winpty أُزيل نهائياً** في سلسلة 1.2.0: المتطلب هو **ConPTY** أي ويندوز 10 إصدار 1809+
  — مقبول تماماً كحد أدنى لنظام «سطر».
- **ثنائيات مسبقة البناء (prebuilds)**: الإصدارات الحديثة تشحن prebuilds في حزمة npm
  لعدة منصات (fork مثل [@lydell/node-pty](https://github.com/lydell/node-pty) وُجد أصلاً
  لتقليم prebuilds الرسمية الكثيرة). إن لم تغطِّ الـ prebuilds نسخة ABI الخاصة بـ Electron
  لدينا، فإن electron-builder يعيد البناء تلقائياً (`npmRebuild` افتراضياً)، وهذا يتطلب على
  **جهاز البناء فقط** (لا أجهزة المستخدمين): Python + أدوات بناء C++‏ (Visual Studio Build
  Tools) + مكتبات Spectre-mitigated (خطأ MSB8040 الشهير إن غابت).
- **التحزيم**: ملفات `.node` لا تعمل من داخل asar. electron-builder يكشف الوحدات الأصلية
  ويفكّها تلقائياً إلى `app.asar.unpacked` (smart unpack)، مع `asarUnpack` احتياطاً.
  يجب التحقق أيضاً من وصول `conpty.node` و`conpty.dll`/OpenConsole المرافقة بعد التحزيم
  (قضايا معروفة مثل [node-pty#372](https://github.com/microsoft/node-pty/issues/372)).
- **إثبات إنتاجي**: VS Code وTabby وHyper كلها Electron + node-pty على ويندوز منذ سنوات —
  المسار معبَّد.

### 2.4 كسر قاعدة «صفر اعتماديات» — استثناء واعٍ

القاعدة 5 في CLAUDE.md تقصر اعتماديات العملية الرئيسية على SDK. الطرفية تستحيل بلا
pseudoterminal حقيقي، ولا بديل خالص بـ JS له (spawn العادي لا يعطي TTY فلا ألوان ولا
تفاعلية ولا ConPTY). **القرار**: نوثّق node-pty كاستثناء مبرَّر وحيد في CLAUDE.md عند
تنفيذ 8.1 — اعتمادية من مايكروسوفت، تشغّل VS Code، بديلها الوحيد كتابة binding أصلي بأنفسنا.

## 3. المقاربات الثلاث للعرض

### المقاربة (أ): xterm.js + ترقيع BiDi فوقه

فكرة: نستخدم xterm.js كاملاً (عرضه DOM أو WebGL) ونحاول حقن BiDi فوقه — عارض مخصص
(Renderer API) أو تعديل DOM بعد الرسم أو CSS.

| الجانب | التقييم |
|---|---|
| تشكيل الحروف | ❌ عارض xterm.js يرسم **خلية-خلية** (حرفاً منعزلاً في مربع)؛ التشكيل العربي يتطلب رسم السطر كسلسلة واحدة — تعارض جوهري مع الشبكة |
| إعادة الترتيب | ❌ يجب تنفيذ خوارزمية BiDi يدوياً وعكس الخلايا، فينكسر التحديد والمؤشر (الافتراض عمود منطقي = بصري) |
| CSS على DOM renderer | ❌ العارض DOM يضع كل خلية في span منفصل — `unicode-bidi` لا يعمل عبر حدود العناصر بهذا الشكل، والتشكيل لا يحدث بين spans |
| Renderer API | ❌ القضية [xterm.js#2005](https://github.com/xtermjs/xterm.js/issues/2005): واجهة العارض داخلية غير مستقرة؛ عارض مخصص = fork صيانته علينا للأبد |
| tmux/vim | ✅ يعمل (كما هو، بلا عربية) |

**الحكم: مرفوضة.** ترقيع لا يعالج التشكيل أصلاً، ويحارب معمارية المكتبة، وينتهي بـ fork
غير قابل للصيانة. لو كان الحل سهلاً من فوق لما بقيت #701 مفتوحة تسع سنوات.

### المقاربة (ب): محلّل ANSI + عرض HTML خالص

فكرة: node-pty يبث البايتات، نحلّل ANSI بأنفسنا، ونرسم كل سطر عنصر HTML — المتصفح
يتكفّل بـ BiDi والتشكيل مجاناً (نفس نهج محادثة «سطر» الناجح).

| الجانب | التقييم |
|---|---|
| العربية | ✅ كاملة ومثالية (Chromium: BiDi + تشكيل + خطوط) |
| كلفة التحليل | ❌ **ضخمة إن كتبناه يدوياً**: ANSI/VT ليس ألواناً فقط — تحريك مؤشر، مسح مناطق، شاشة بديلة، أوضاع، عناوين، OSC… إعادة اختراع نصف xterm.js |
| تطبيقات TUI | ❌ vim/htop تحتاج شبكة خلايا كاملة وتحديث عشوائي الوصول — نموذج «أسطر HTML» ينهار |
| الأداء | ⚠️ يحتاج ضبطاً (سقف scrollback + تحديث تفريقي)، لكنه مجدٍ لسيناريو الأوامر السطرية |

**تحسين حاسم يغيّر المعادلة**: بدل كتابة المحلّل، نستخدم **xterm.js نفسه كمحرك حالة**
(نسخة كاملة مخفية أو `@xterm/headless`): هو يحلّل ANSI ويدير الشبكة والشاشة البديلة
والألوان، ونحن نقرأ **Buffer API** العام ونرسم الأسطر HTML. صفر تحليل يدوي، وصيانة
المحلّل على فريق xterm.js/VS Code.

### المقاربة (ج): الهجين — محرك واحد، عارضان

فكرة: **نسخة xterm.js واحدة** هي محرك الحالة الدائم، وفوقها عارضان يتبادلان تلقائياً:

1. **عرض BiDi‏ (HTML)** — الافتراضي: يرسم أسطر الشبكة العادية (normal buffer) كعناصر HTML
   بأسلوب المحادثة: `unicode-bidi: plaintext` لكل سطر (اتجاه تلقائي حسب المحتوى)، مقاطع
   الألوان spans، الأكواد والمسارات LTR ضمن السطر. هنا تعيش العربية: `git status`،
   `dir`، مخرجات السكربتات، رسائل الأخطاء.
2. **عرض الشبكة (xterm.js الأصلي)** — للتطبيقات كاملة الشاشة: عند تفعيل الشاشة البديلة
   (`buffer.onBufferChange` → alternate: أي vim/htop/less) نظهر عارض xterm.js الأصلي
   بدقته الكاملة (بلا عربية — كما كل طرفيات الدنيا اليوم)، وعند الخروج نعود لعرض BiDi.

| الجانب | التقييم |
|---|---|
| العربية حيث تهم | ✅ مثالية في وضع الأوامر السطرية (99% من حالات الاستخدام المستهدفة) |
| tmux/vim | ✅ تعمل عبر xterm.js الأصلي — لا ننكسر، فقط لا نُحسّن (مؤقتاً) |
| التحليل | ✅ صفر تحليل يدوي — xterm.js هو المحلّل الوحيد |
| التبديل | ✅ إشارة موثوقة وعامة (`onBufferChange`) لا استدلال هشّاً |
| المخاطرة | ⚠️ ترجمة المؤشر والتحديد في عرض BiDi علينا (القسم 6) |

## 4. التوصية

**المقاربة (ج) الهجينة، بمحرك xterm.js واحد وعارضين.** الأسباب:

1. **لا نراهن ضد الفيزياء**: التشكيل العربي داخل شبكة خلايا (أ) معركة خاسرة خاضها الجميع
   وخسرها؛ والمتصفح يجيدها منذ عقدين. نضع العربية حيث يتفوق المتصفح، والشبكة حيث تتفوق الشبكة.
2. **لا نعيد اختراع محلّل VT** (سقوط المقاربة ب الخالصة): xterm.js يبقى المحلّل، بواجهة
   Buffer عامة وموثّقة، فنرث سنوات نضج VS Code.
3. **متوافقة مع مواصفة freedesktop**: BiDi عرضٌ فقط، الوضع الضمني افتراضياً، المخزن منطقي —
   تنفيذنا يطابق روح المواصفة التي طبّقتها VTE، والمتصفح ينفّذ خوارزمية BiDi نفسها.
4. **تدرّج آمن**: 8.1 تسلّم طرفية عاملة عادية (قيمة فورية حتى قبل العربية)، وكل مرحلة تالية
   تضيف طبقة قابلة للقياس، ولا توجد نقطة «كل شيء أو لا شيء».
5. **مسار ترقية مفتوح**: لاحقاً يمكن تجربة BiDi حتى في وضع الشاشة البديلة (عرض HTML للشبكة
   كاملة) — الخندق يتعمق بلا إعادة هدم.

## 5. نطاق النسخة الأولى (MVP)

### تفعل ✅

- تبويب/لوحة «طرفية» داخل «سطر» يشغّل الصدفة الافتراضية (PowerShell على ويندوز) عبر
  node-pty/ConPTY في `cwd` المشروع الحالي.
- عرض BiDi للأوامر السطرية: مخرجات عربية **مشكّلة الحروف وصحيحة الاتجاه** (echo عربي،
  أسماء ملفات عربية في dir/git status، مخرجات سكربتات عربية)، مع نصوص مختلطة سليمة
  (أمر إنجليزي + خرج عربي)، والأرقام والمسارات LTR داخل السطر.
- ألوان ANSI الأساسية (16 لوناً + 256 + truecolor عبر سمات خلايا xterm.js) وسمات
  غامق/خافت/مائل/تسطير.
- إدخال أساسي: كتابة بالعربية والإنجليزية، Enter،‏ Ctrl+C، أسهم التاريخ (تمرَّر للصدفة)،
  لصق. سطر الإدخال عنصر HTML بحق (والعربية فيه مثالية بالتعريف).
- تمرير (scrollback) بسقف، وتحديد ونسخ في عرض BiDi (نسخ نصي بسيط).
- تطبيقات الشاشة الكاملة **لا تنكسر**: تُفتح في عارض xterm.js الأصلي وتعود تلقائياً.
- قتل عملية الطرفية عند إغلاق «سطر» (نفس فلسفة bgprocs).

### لا تفعل صراحةً ❌ (مؤجل، ليس نقصاً خفياً)

- **لا** عربية داخل تطبيقات TUI كاملة الشاشة (vim/htop) — تعمل بالسلوك العالمي الحالي (LTR).
- **لا** تعدد تبويبات/تقسيم — طرفية واحدة.
- **لا** إعادة تدفق عند تغيير العرض في عرض BiDi (سلوك أساسي فقط).
- **لا** روابط قابلة للنقر، بحث في المخرجات، ثيمات — تلميع لاحق.
- **لا** دعم أنظمة أقدم من ويندوز 10 1809 (متطلب ConPTY، يُوثَّق كحد أدنى).
- **لا** كمال في حالات BiDi الحدّية النادرة (ترقيم مختلط معقد) — «أفضل من أي طرفية موجودة»
  هو المعيار، لا الكمال المطلق.

## 7. تقسيم المراحل الفرعية

### 8.1 — الأساس: node-pty + طرفية xterm.js عادية

- إضافة node-pty (استثناء الاعتماديات يُوثَّق في CLAUDE.md) والتحقق من البناء المحلي
  وprebuilds/إعادة البناء لـ Electron.
- `electron/term.js` جديد: إنشاء pty (صدفة، cwd، أبعاد)، قناة IPC للبايتات (اتجاهان)،
  تغيير الحجم، الإنهاء، قتل عند الإغلاق. تنقية صارمة للمعرّفات (نمط `SAFE_*` القائم).
- واجهة: لوحة طرفية بعارض xterm.js قياسي (بلا عربية بعد).
- **التحقق الحرج**: `npm run dist` — المثبّت يعمل على جهاز نظيف والوحدة الأصلية تُحمَّل
  من `app.asar.unpacked`.

**قبول 8.1:** أفتح الطرفية، أنفّذ `dir` و`git status` وأرى الخرج بألوانه؛ `python` تفاعلي
يعمل؛ Ctrl+C يقطع؛ إغلاق «سطر» يقتل الصدفة. (بند المثبّت مؤجَّل لفحص نهائي واحد قبل
الإصدار — قرار أسلوب القبول في PLAN.md؛ التحزيم نفسه تحقَّق آلياً في 8.1.)

### 8.2 — عرض BiDi للمخرجات (قلب المرحلة)

- طبقة قراءة من Buffer API: ترجمة أسطر الشبكة العادية إلى HTML (سطر = عنصر،
  `unicode-bidi: plaintext`، مقاطع الألوان/السمات spans، أرقام ومسارات LTR).
- تحديث تفريقي: إعادة رسم الأسطر المتغيرة فقط، سقف scrollback، دفعات rAF.
- عرض BiDi هو الافتراضي؛ عارض xterm.js مخفي (التبديل اليدوي مؤقتاً للتجربة).

**قبول 8.2:** `echo "مرحبا بالعالم"` يظهر مشكّلاً RTL؛ `git status` بملفات عربية الأسماء
صحيح؛ سكربت python يطبع عربياً ومختلطاً (عربي + مسار + أرقام) فيُعرض كل جزء باتجاهه؛
مخرجات build غزيرة لا تجمّد الواجهة **وفق معيار القياس الملزم في القسم 8.4**
(استجابة < 100م.ث أثناء الفيضان + استقرار الذاكرة عند سقف 5000 سطر).

### 8.3 — الإدخال والتحديد

- سطر إدخال HTML أسفل العرض: كتابة عربية/إنجليزية مثالية، Enter يرسل للـ pty،
  أسهم/Tab/Ctrl+C تمرَّر مباشرة، لصق آمن (bracketed paste).
- تحديد ونسخ من عرض BiDi (نسخ المنطقي الصحيح لا البصري).
- صدى محلي مضبوط (التعامل مع echo الصدفة كي لا يتكرر السطر).

**قبول 8.3:** عقد الإدخال في القسم 8.3 بكامله: أكتب أمراً فيه اسم ملف عربي وينفَّذ (بلا
ازدواج عرض — الصدى وحده يظهر)؛ محثّ y/n يُجاب بـ `y`+Enter؛ Ctrl+C يقطع أمراً جارياً
(والحقل غير فارغ: يُفرّغه أيضاً)؛ أستدعي التاريخ بالأسهم وحقل فارغ وEnter ينفّذه؛
أنسخ سطراً عربياً وألصقه في محرر خارجي فيكون سليماً؛ وإكمال Tab لا يعمل **بتصميم موثّق**.

### 8.4 — التبديل التلقائي والتلميع والتوثيق

- `buffer.onBufferChange`: شاشة بديلة ⇐ عارض xterm.js؛ العودة ⇐ عرض BiDi تلقائياً.
- vim/less/htop تُختبر ذهاباً وإياباً؛ مؤشرات حالة عربية («وضع تطبيق كامل الشاشة»).
- تحديث CLAUDE.md (المعمارية، العقود، استثناء الاعتماديات) وPLAN.md، وفحص حجم المثبّت.

**قبول 8.4:** `vim` يفتح في العارض الشبكي ويعمل، `:q` يعيدني لعرض BiDi والعربية تعمل
فوراً؛ جلسة عمل كاملة (أوامر + عربي + vim + عودة) بلا كسر؛ المثبّت النهائي سليم.

## 8. قرارات تصميمية مثبّتة (إجابات مراجعة التصميم — قبل بناء 8.2/8.3)

### 8.1 تأكيد المعمارية: نسخة xterm.js حقيقية **واحدة** لا محرّكان

**القرار: نسخة xterm.js حقيقية واحدة، مثبّتة دائماً في DOM، هي مصدر الحقيقة الوحيد.**

- عرض BiDi‏ HTML هو **إسقاط (projection) للقراءة فقط** من Buffer الخاص بهذه النسخة —
  لا محرك ثانٍ، لا تحليل مزدوج، **فلا مشكلة مزامنة أصلاً** (لا يوجد طرفان يتزامنان).
- الإدخال في الاتجاهين يمر عبرها أيضاً: في وضع الشاشة البديلة `term.onData` → pty مباشرة؛
  في وضع الأسطر، سطر الإدخال HTML يكتب إلى pty مباشرة (النسخة تتلقى النتيجة عبر خرج pty).
- الإخفاء في وضع الأسطر يكون بـ `visibility: hidden` مع إبقاء أبعاد حقيقية للحاوية
  (**لا** `display: none`): العارض يحتاج أبعاداً صالحة كي تبقى الشبكة/الالتفاف صحيحة
  ويبقى التبديل للشاشة البديلة فورياً بلا إعادة قياس. مصدر إشعارات التغيير لعرض BiDi هو
  `onWriteParsed` (يعمل بمعزل عن دورة الرسم) لا `onRender` (قد لا يُطلق والعارض مخفي).
- رُفض البديل (headless + نسخة مرئية منفصلة) صراحةً: محلّلان يستهلكان نفس البايتات
  بحالتين منفصلتين = انجراف حتمي (scrollback مختلف، أبعاد مختلفة، سباقات) بلا أي مكسب.

### 8.2 الصدى (Echo): الاعتماد على صدى الصدفة، لا كبت ولا ازدواج

**القرار: سطر الإدخال HTML عابر (transient) — يُفرَّغ عند الإرسال، وسطر الأمر المعروض
الوحيد هو صدى الصدفة نفسه القادم في خرج pty.**

- التسلسل: المستخدم يؤلّف السطر في حقل HTML (عربية مثالية أثناء الكتابة)؛ عند Enter
  يُرسل السطر + `\r` إلى pty **ويُفرَّغ الحقل فوراً**؛ الصدفة تعيد السطر (صدى) ملحقاً
  بسطر الموجّه (prompt) في الشبكة، وعرض BiDi يعرضه كأي سطر خرج. **لا ازدواج بالبناء** —
  النسخة الوحيدة المعروضة بشكل دائم هي صدى الصدفة.
- لماذا لا «كبت الصدى»؟ على ويندوز/ConPTY لا يملك المضيف مقبض termios لإطفاء echo،
  وترشيح البايتات المُصدّاة هشّ حتماً: PSReadLine في PowerShell **يعيد رسم** السطر بتلوين
  نحوي (ليس نسخة حرفية مما أرسلناه)، فأي مطابقة نصية ستفشل. الاعتماد على الصدى هو
  السلوك القياسي الصحيح، ويمنحنا مجاناً: سجلّ الأوامر في التمرير، وتلوين PSReadLine.
- مكسب جانبي حاسم: «المؤشر الملعون» (القسم 6) يُحل جذرياً — المؤشر أثناء التأليف هو مؤشر
  حقل HTML الحقيقي (المتصفح يديره بكمال في BiDi)، ولا نرسم مؤشراً بصرياً داخل أسطر الشبكة.
- حالة حدّية موثّقة: كلمات المرور (echo مطفأ لدى الصدفة) لن تظهر في الشبكة — صحيح —
  لكنها **تظهر أثناء الكتابة في حقل HTML المحلي**. لا سبيل موثوقاً لاكتشاف وضع echo عبر
  ConPTY، فالحل في 8.3 زر 👁 يدوي يحوّل الحقل إلى `type=password` (اختياري، غير حرج للقبول).

### 8.3 حدود الإدخال التفاعلي — عقد الـ MVP الدقيق (يدخل في قبول 8.3)

مبدأ حاكم: القيود التالية تخص **وضع الأسطر (عرض BiDi) فقط**. في وضع الشاشة البديلة
(vim/less/htop) الإدخال **خام بالكامل** عبر `term.onData` — كل مفتاح يصل pty كما هو،
بلا أي وساطة من حقل HTML.

**مدعوم في وضع الأسطر (v1):**

| القدرة | الآلية |
|---|---|
| أسطر منتهية بـ Enter | السطر كاملاً + `\r` إلى pty (يشمل أوامر بأسماء ملفات عربية) |
| محثّات y/n والمحثّات النصية | نفس آلية السطر: `y` + Enter — كل المحثّات التي تقرأ سطراً تعمل |
| «اضغط أي مفتاح» / pause | Enter وحقل فارغ ⇐ يُرسل `\r` خاماً — يُرضي الغالبية الساحقة |
| **تمرير مفاتيح خام موثّق** (وحقل الإدخال **فارغ**) | Ctrl+C ⇐ `\x03` (يعمل أيضاً والحقل غير فارغ: يرسل `\x03` **ويفرّغ الحقل المحلي**)؛ Ctrl+Z ⇐ `\x1a`؛ Ctrl+D ⇐ `\x04`؛ سهم أعلى/أسفل ⇐ `\x1b[A`/`\x1b[B` (تاريخ الصدفة — الاستدعاء يظهر كصدى في الشبكة، وEnter بحقل فارغ ينفّذه) |
| أسهم يمين/يسار/Home/End والحقل غير فارغ | تحرير **محلي** داخل الحقل (مؤشر المتصفح) |
| لصق | نص الحافظة يدخل الحقل محلياً (متعدد الأسطر يُرسل كما هو عند Enter) |
| كلمات المرور | تعمل (تُرسل كسطر)؛ تُعرض محلياً أثناء الكتابة — انظر 8.2 أعلاه |

**غير مدعوم صراحةً في وضع الأسطر (مؤجل، ليس عيباً خفياً):**

- **إكمال Tab**: مستحيل بالبناء في وضع الأسطر — الصدفة لم ترَ البادئة (نرسل عند Enter فقط)،
  فلا تملك ما تكمله. البديل المستقبلي الموثّق: «وضع بث الحروف» (إرسال كل ضغطة خاماً)
  كمرحلة لاحقة، أو استخدام vim/التطبيقات الشاشية حيث الإدخال خام أصلاً.
- **قوائم الاختيار السهمية السطرية** (inquirer وأشباهها التي تقرأ مفاتيح خام دون شاشة بديلة):
  قد لا تعمل بسلاسة — الأسهم تمرَّر فقط والحقل فارغ، وقد يتداخل العرض. تُوثَّق كحد معروف.
- **تحرير سطر الصدفة عن بُعد** (Ctrl+A/Ctrl+E/Ctrl+R بحث التاريخ التفاعلي): لا تمرَّر في v1.

### 8.4 استراتيجية الأداء لعرض BiDi (تدخل في قبول 8.2)

**مسار البيانات**: pty ⇐ `term.write()` (محلّل xterm.js يجمع دفعاته داخلياً) ⇐ حدث
`onWriteParsed` يعلّم «متسخ» فقط ⇐ **مزامنة مُجمَّعة بـ requestAnimationFrame**
(سقف طبيعي ~60 مزامنة/ث مهما بلغ فيضان الخرج).

1. **تقسيم ثابت/حيّ**: الأسطر التي خرجت من نافذة العرض إلى scrollback في xterm.js
   **غير قابلة للتغيير** — تُحوَّل إلى HTML مرة واحدة عند انزلاقها (يُكتشف بفرق
   `buffer.baseY`) ولا تُلمس بعدها. «المنطقة الحية» (صفوف نافذة العرض فقط، ≤ ارتفاع
   الطرفية) هي وحدها المرشحة لإعادة الرسم كل إطار.
2. **تحديث تفريقي للمنطقة الحية**: لكل صف حيّ نخزّن بصمة (النص + السمات)؛ لا يُعاد بناء
   عنصر السطر إلا إذا تغيّرت بصمته — أشرطة progress التي تعيد رسم سطرها تكلّف تحديث
   عنصر واحد لا أكثر (وهذا يعالج خطر «البرامج التي تعيد رسم سطرها» من القسم 6).
3. **سقف صارم**: `scrollback: 5000` في xterm.js، وDOM عرض BiDi حلقة بنفس السقف —
   يُحذف الأقدم مع كل إضافة. عدد عقد DOM محدود ⇒ ذاكرة محدودة.
4. **عزل تخطيط رخيص**: `content-visibility: auto` (+`contain-intrinsic-size` بارتفاع سطر
   ثابت) على عناصر الأسطر — المتصفح يتخطى تخطيط ورسم ما هو خارج الشاشة، أي «افتراضية»
   مدمجة بلا مكتبات. **الافتراضية اليدوية (windowing) مؤجلة عمداً**: لا تُبنى إلا إذا أثبت
   القياس في 8.2 الحاجة.
5. **صمام الضغط الخلفي (احتياطي موثّق)**: إن أظهر القياس تكدّساً رغم ذلك، node-pty يوفّر
   `pause()/resume()` وxterm.js يوفّر callback لـ `write()` — يمكن ربطهما لإبطاء المصدر.
   لا يُفعَّل في v1 إلا عند الحاجة المقيسة.

**معيار قياس ملزم في 8.2**: خرج غزير (`npm install` أو build كامل) لا يجمّد الواجهة —
كتابة في حقل الإدخال أثناء الفيضان تستجيب < 100م.ث، والذاكرة تستقر عند سقف الـ 5000 سطر.

**ملاحظات تنفيذ 8.2 (انحرافان موثَّقان عن الخطة أعلاه):**

1. **الإسقاط النافذي بدل «الثابت/الحي + الإلحاق مرة واحدة»**: أثناء التنفيذ تبيّن أن كشف
   «انزلاق الأسطر إلى scrollback» عبر فرق `buffer.baseY` **ينكسر عند تشبّع الـ scrollback**
   (يثبت baseY عند السقف بينما تستمر الأسطر بالانزلاق — فيتوقف الإلحاق ويضيع الخرج).
   الحل المعتمد أبسط وأصح: **إسقاط نافذي عديم الحالة** — DOM لا يحوي إلا أسطر نافذة
   التمرير المرئية (+OVERSCAN)، والفاصل (spacer) بارتفاع `buffer.length × 20px` يمثل
   الكل، وxterm يبقى مالك الـ scrollback الوحيد (وهو الأوفى لمبدأ «محرك واحد»). البصمة
   لكل سطر مرئي تبقى (البند 2 أعلاه)، وسقف الذاكرة يتحقق بنيوياً (عناصر DOM ≈ ارتفاع
   الشاشة لا 5000). بند `content-visibility` سقط لانتفاء الحاجة (لا DOM خارج الشاشة أصلاً).
2. **إخفاء الشبكة في وضع BiDi بـ `opacity:0` لا `visibility:hidden` (مؤقت حتى 8.3)**:
   الإدخال في 8.2 ما يزال عبر حقل xterm المخفي، و`visibility:hidden` يمنع التركيز عليه
   فتنقطع الكتابة للـ pty. بعد بناء سطر الإدخال HTML في 8.3 يُعاد تقييم الإخفاء.
